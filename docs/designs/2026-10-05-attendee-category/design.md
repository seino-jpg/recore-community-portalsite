# 参加者の区分タグと、運営による参加者登録

状態: 確定（2026-10-05 合意）


## 課題

コミュニティイベントには、お客さん以外に RECORE 社内（開発・セールス）、ベンダー、運営の人も参加する。今は次の点が困る。

| 困りごと | 今のやり方（関東 Vol.4） |
|---|---|
| 社内の参加者を入れる手段がない | 締切後のため、シートに手で1行足した（10/5 社内の4名）。自動返信も Slack も出ない |
| お客さんと社内が一覧で見分けられない | 会社名「株式会社RECORE」で目視 |
| 会場に伝える人数の内訳が出ない | 合計人数しか出ない。お客さんが何名か、関係者が何名かを数え直す |

## 解決した状態

- /admin に「＋参加者を登録」があり、運営メンバーなら誰でも、区分・会社名・氏名・台数だけで1件登録できる。締切後でも登録できる
- 申込1件ごとに **区分（一般参加者／RECORE／ベンダー／運営）** を持ち、一覧に区分の列と絞り込みが出る
- 集計の「合計参加人数」は全員で数え、その下に区分別の内訳が出る。残り枠も全員で数える（会場に伝える人数と一致させる）

## 前提

| 前提 | 理由 |
|---|---|
| PR #8（DB・API）と PR #9（フォーム・/admin の切替）の上に載せる。**この機能は移行の切替が済んでから着手する** | シート版の GAS は廃止が決まっている。シートに区分列を足しても移行で作り直しになる |
| 関東 Vol.4 は今のまま（お客さんと同じフォーム・シート）。この機能は関西 Vol.2 以降で使う | ブックオフさんへの準備依頼が今のフォームの情報で動いている |

## 設計の意図

PR #8 の D1〜D20 はそのまま。足すのは次の D21〜D27。

| # | 決めたこと | 理由 | 採らなかった案 |
|---|---|---|---|
| D21 | 区分は**申込1件（行）ごと**に1つ持つ。値は `general`（一般参加者）・`recore`（RECORE）・`vendor`（ベンダー）・`staff`（運営）の4つで固定。フォームからの申込は `general` | 「代表者まとめ申込」の形（D2）に乗る。同じ行の中で区分が混ざるのは稀で、混ざるなら行を分けて登録すればよい（清野さんの判断） | → 参加者1人ごと: 参加者を別表に分ける必要があり D2 を作り直す。→ 区分を自由入力: 表記ゆれで集計が割れる |
| D22 | 運営による登録は /admin から行い、`source = 'admin'`。**閲覧の許可リストの全員**が登録できる（清野さんの判断） | 社内の参加者を各自がすぐ入れられる。登録は追加だけで、既存の申込者の情報には触れない | → 清野さんだけ: 依頼が清野さんに集まる |
| D23 | 取消・変更は今までどおり**清野さんだけ**（D13 のまま）。変更できる項目に「区分」を足す | 登録できる人を広げても、他人の行を書き換えられる人は1人のまま。移行で入った行（例: 株式会社RECORE）の区分を後から直せる | → 登録した本人も取消可: 「誰が登録したか」で権限が変わり API の照合が増える |
| D24 | 登録の入力は **区分・会社名・参加者氏名（1名以上）・車の台数・メモ（任意）**。区分が RECORE なら会社名は「株式会社RECORE」を自動で入れる。代表者は氏名の先頭。役職・メール・電話は空で持つ | 社内・関係者の連絡先は運営がすでに知っている。入力を最小にして「ぱぱっと」入れられるようにする（清野さんの判断） | → お客さんと同じ項目: 入力が重く、結局シートに手で足すのと変わらない |
| D25 | 登録は**締切後でもできる**（API の締切判定はフォームの申込だけに掛ける） | 社内の参加は締切後に決まることが多い（今回も 10/5 に4名） | — |
| D26 | 運営登録の行には**自動返信メールを送らない**。運営 Slack にだけ「【運営登録】」として流す（登録者のメールを添える）。Cron の再送・「通知未完了」の数からは外す | 宛先のメールが無い。Slack は運営が気づくための通知で、失敗しても登録は成立している（D14 の取消・変更と同じ扱い） | → お客さんと同じ申込通知: メール欄が空の通知が「未完了」として残り続ける |
| D27 | 集計: 合計参加人数・残り枠・合計台数は**全区分で数える**。申込社数は**一般参加者の行だけ**で数える。区分別の人数を内訳として出す | 会場に伝える人数と残り枠を一致させる（清野さんの判断）。「社数」はお客さんの社数として使っているため | → 残り枠は一般だけ: 会場の受け入れ人数を超えても気づけない |

## アウトプット

### ① データ定義（`applications` への追加）

| 列 | 型 | 内容 |
|---|---|---|
| `category` | text NOT NULL DEFAULT `'general'` CHECK IN (`general`,`recore`,`vendor`,`staff`) | 区分（D21） |
| `source` | 既存。CHECK に `'admin'` を追加 | 運営登録（D22） |
| `role`・`email`・`tel` | 既存（NOT NULL のまま）。運営登録では空文字 | D24 |

`application_changes.action` の CHECK に `'create'` を追加し、運営登録を「誰が・いつ」で残す（after に登録内容）。

既存行の区分の初期値:

| 行 | 区分 |
|---|---|
| フォーム・転送・移行で入った行 | `general` |
| 移行で入った「株式会社RECORE」の行（10/5 に手で足した社内4名） | `recore`（スキーマ適用時に1回だけ更新） |

### ② 処理の流れ

| 操作 | 誰が | API（`/api/admin`） | 通知 |
|---|---|---|---|
| 一覧 | 閲覧の全員 | `list`：行に `category`、集計に区分別人数を足す。`canRegister`（閲覧者は常に true）を返す | — |
| 登録 | 閲覧の全員 | `register`（新規）：区分・会社名・氏名・台数・メモを検証 → 行と履歴 `create` を1文で保存。締切は見ない | 運営 Slack に【運営登録】（GAS の `notify_change` に `type = register` を追加） |
| 区分の変更 | 清野さん | `update` の変更可能項目に `category` を追加 | 今までどおり【申込変更】 |
| 取消 | 清野さん | 変更なし | 変更なし |
| Cron・再送 | — | 対象から `source = 'admin'` を外す | — |

### ③ 画面（/admin）の前後

数字は関東 Vol.4 の 10/5 時点（お客さんの重複1件を取消した前提）。

```
【Before（PR #9）】
┌ 申込社数 14社 ┬ 合計参加人数 27名 ┬ 残り枠 -7名 ┬ 合計車台数 6台 ┐
│ 受付日時 │ 会社名 │ 代表者 │ 役職 │ メール │ 電話 │ 人数 │ 氏名 │ 台数 │ … │ 状態 │ 通知 │

【After】
┌ 申込社数 14社 ┬ 合計参加人数 31名            ┬ 残り枠 -11名 ┬ 合計車台数 7台 ┐
│ （一般のみ）  │ 一般27・RECORE4・ベンダー0・運営0 │ 定員20名    │                │
[すべて 15] [一般 14] [RECORE 1] [ベンダー 0] [運営 0]          [＋参加者を登録]
│ 受付日時 │ 区分 │ 会社名 │ 代表者 │ … │ 状態 │ 通知 │
│ 10/05 18:26 │ RECORE │ 株式会社RECORE │ 社内 一郎 │ … │ 有効 │ 運営登録 │

＋参加者を登録（パネル）
  区分     ( ) RECORE  ( ) ベンダー  ( ) 運営  ( ) 一般参加者
  会社名   [株式会社RECORE      ]   ← RECORE を選ぶと自動入力
  参加者   [社内 一郎] [社内 二郎] [社内 三郎] [社内 四郎] [＋1名追加]
  車の台数 [1台 ▼]
  メモ     [社内参加                ]
                                  [登録する]
```

区分は色付きのラベルで表示し、一般参加者は無地にする（お客さんの行を基準として見やすく）。

## ユースケース

| # | 場面 | 期待する結果 |

| U27 | 閲覧者（清野さん以外）が RECORE を2名登録 | 行が1件増え、区分 RECORE・会社名 株式会社RECORE。合計人数 +2・残り枠 -2・社数は変わらない。Slack に【運営登録】と登録者 |
